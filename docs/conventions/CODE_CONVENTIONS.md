# 팀 코드 컨벤션

VetConsult는 **단일 레포 · 모놀리식 애플리케이션**이다.
내부만 도메인 모듈 + 헥사고날로 나눈다. (MSA 아님)

Git: `GIT_CONVENTIONS.md` · 설정: `CONFIG.md`

---

## 0. 팀 필수 규칙

1. **SOLID** 준수
2. **불필요한 `static` 사용 금지**
3. **헥사고날 아키텍처** 유지 (모놀리식 **내부** 모듈 구조)
4. **다른 팀원의 코드를 건드리지 않기**
5. **애매하면 혼자 판단하지 말고 물어보기**
6. **`@Setter` / `@AllArgsConstructor` 남발 금지** (데이터 정합성)
7. **맡은 도메인의 API 명세를 `docs`에 도메인별로 작성·유지**

---

## 0.1 단일 레포 · 모놀리식

| 항목 | 규칙 |
|------|------|
| 레포 | **하나**. 기능마다 새 서비스 레포를 만들지 않는다. |
| 배포 | **앱 하나**로 빌드·기동·배포한다. |
| 내부 구조 | 도메인 모듈(`clinic`, `matching`, `care` …) + 각 모듈 `domain` / `application` / `adapter` |
| 모듈 간 호출 | 공개 입력 포트(또는 합의된 application API)로만. 다른 모듈의 영속성·Controller 직접 참조 금지 |
| 팀 작업 단위 | 레포가 아니라 **모듈·패키지·이슈** 단위로 나눈다 |

MSA 전제(서비스별 Eureka 등록 필수, 서비스 간 HTTP만으로만 통신 등)로 설계하지 않는다.
공용 MySQL·Kafka·Mongo는 **같은 모놀리식 앱**이 접속한다.

## 1. 협업

### 다른 팀원의 코드를 건드리지 않기

- 맡은 이슈·**도메인 모듈**·파일만 수정한다.
- 다른 사람 PR·브랜치 범위의 파일을 편의상 수정하지 않는다.
- `shared` / `global` 또는 모듈 경계를 넘는 변경은 이슈·채팅으로 **합의 후** 진행한다.

### 팀원 코드인지 구별하는 방법

자동으로 “내 파일 / 남의 파일”이 표시되지는 않는다. 아래를 **순서대로** 확인한다.

| 순서 | 방법 | 보는 것 |
|------|------|---------|
| 1 | **이슈·PR** | 이슈 Assignee, PR 작성자·리뷰 범위. **내가 맡은 이슈에 없는 파일**은 기본적으로 남의 작업으로 본다. |
| 2 | **도메인 모듈 소유** | 팀에서 정한 모듈 담당(예: matching / clinic / care). 담당이 아닌 모듈은 합의 없이 수정하지 않는다. |
| 3 | **Git 이력** | `git blame <파일>`, `git log -- <파일>` — 최근·주요 작성자가 나라면 내 작업, **다른 팀원이면 합의 후**. |
| 4 | **열린 PR·브랜치** | 같은 파일을 다른 사람 `feat/...` 브랜치·PR이 잡고 있으면 **건드리지 않거나** 그 사람에게 먼저 말한다. |
| 5 | **CODEOWNERS** (도입 시) | 레포 루트 `.github/CODEOWNERS`에 경로별 담당자를 두면 GitHub이 리뷰어로 잡는다. 소유 기준을 문서화할 때 권장. |

**내 코드로 봐도 되는 경우**

- 내가 Assignee인 이슈·내가 연 브랜치/PR에서 추가·수정한 파일
- 팀이 내게 배정한 도메인 모듈 안의 파일 (이슈 범위 안)

**남의 코드 / 합의 필요한 경우**

- blame·log상 다른 팀원이 주로 작성·유지하는 파일
- 다른 사람 이슈·PR에 포함된 파일
- `shared` / `global` · 공통 설정 · 모듈 경계 API

애매하면 **수정하지 말고** 담당자·팀장에게 물어본 뒤 진행한다. (아래 「애매하면 물어보기」)

### 애매하면 물어보기

추정으로 구현하지 않는다. 다음이면 팀원·팀장에게 확인한다.

- 스키마·토픽·상태 전이·모듈 소유가 문서와 다를 때
- 모듈/포트 경계를 넘어야 할 때
- 설계 선택이 불명확할 때
- 다른 사람 코드와 충돌·중복이 의심될 때

## 2. 공통 원칙

- 먼저 기존 프로젝트의 구조, 기술 스택, 코딩 컨벤션, 클래스 간 의존관계를 분석한다.
- 기존 코드와 일관성을 유지하며, 요구사항과 관련 없는 코드는 임의로 변경하지 않는다.
- 동작하지 않는 예시·의사 코드가 아니라 **완성된 코드**를 작성한다.
- 존재하지 않는 클래스, 메서드, 엔티티, DTO, API를 임의로 가정하지 않는다.
- 필요한 정보가 없으면 가정한 내용을 명확히 표시하고, 가능하면 먼저 확인한다.
- 유지보수성, 확장성, 테스트 용이성, 가독성을 우선한다.
- 단순한 기능에 불필요한 추상화·패턴을 넣지 않는다.
- 보안, 예외 처리, 입력 검증, 데이터 정합성을 함께 고려한다.
- 변경 대상 파일과 변경 이유를 명확히 설명한다.

## 3. SOLID

### SRP

- Controller: 요청 수신, 입력 검증, 응답 반환
- Service: 비즈니스 로직과 트랜잭션
- Repository / 영속성 어댑터: 데이터 접근
- DTO: 계층 간 전달
- Entity / 도메인: 상태
- 한 클래스·메서드에 여러 책임을 몰지 않는다.

### OCP

- 기능 추가 시 기존 코드를 넓게 고치지 않도록 설계한다.
- 확장 가능성이 낮은 단순 로직에는 불필요한 추상화를 넣지 않는다.

### LSP

- 구현체는 상위 계약을 깨지 않는다.
- 상속보다 조합이 맞으면 조합을 우선한다.

### ISP

- 역할별 작은 포트/인터페이스를 쓴다.
- 쓰이지 않는 범용 CRUD를 출력 포트에 넣지 않는다.
- 구현이 하나뿐이고 확장 계획이 없으면 형식적 인터페이스만 만들지 않는다.

### DIP

- 업무 로직은 구체 어댑터가 아니라 **포트**에 의존한다.
- **생성자 주입** (`@RequiredArgsConstructor` + `final`). 필드 주입 금지.
- 외부 API·메시징 등은 추상 경계를 통해 접근한다.

### 백엔드 추가

- 메서드는 하나의 작업만 수행한다.
- 트랜잭션은 Service에서 명확히 둔다.
- Entity를 Controller 응답으로 직접 반환하지 않는다. Request/Response DTO 사용.
- DTO↔Entity/도메인 변환 책임을 분리한다.
- 의미 있는 업무 예외 + 전역 예외 처리를 우선한다.
- 조회와 변경 책임을 구분한다.
- N+1·불필요 전체 조회·과도한 반복 쿼리를 피한다.

## 4. 불필요한 static 금지

**허용:** `private static final` 상수, DTO/Command `of`·`from`, 도메인 `create`·`restore`, 순수 매퍼(남용 금지), 테스트 정적 import

**금지:** 서비스/어댑터 업무 로직 static, 가변 static, 빈·DB·시계를 숨긴 정적 헬퍼

## 5. 헥사고날 (모놀리식 내부)

하나의 Spring Boot 앱 안에서 **도메인 모듈**을 나누고, 모듈마다 헥사를 적용한다.  
패키지 루트(서비스명) 예: `com.pethealthconsult` (레포: `pet-health-consult-be`)

### 5.1 패키지 구조 (필수)

도메인 이름은 `matching` 자리만 바뀐다. 사람·서비스 폴더(`SHG-*-service` 등)로 나누지 않는다.

```text
com.{서비스명}/
├── matching/          # 도메인 모듈 (매칭 담당)
│   ├── request/
│   ├── wave/
│   ├── offer/
│   └── …
├── clinic/            # 다른 도메인 (다른 담당)
├── care/              # …
├── shared/            # 모듈 공용 (기술 독립)
└── global/            # 설정·공통 웹/영속 지원
```

패키지 FQCN:

```text
com.{서비스명}.matching   ← 매칭 담당
com.{서비스명}.clinic     ← 클리닉 담당
com.{서비스명}.care       ← 케어 담당
com.{서비스명}.shared
com.{서비스명}.global
```

예 (`com.pethealthconsult`):

```text
com.pethealthconsult.matching
com.pethealthconsult.clinic
com.pethealthconsult.care
com.pethealthconsult.shared
com.pethealthconsult.global
```

### 5.2 도메인 모듈 내부 (헥사)

각 도메인(또는 matching의 `request` / `wave` / `offer` 같은 하위 단위)는 아래를 따른다.

```text
…/{도메인}/
├── domain/
├── application/          # usecase · model · port
└── adapter/
    ├── in/               # web · messaging …
    └── out/              # persistence · client …
```

```text
입력 어댑터 → 입력 포트 ← 서비스 → 출력 포트 ← 출력 어댑터
                      서비스·포트 → 도메인
```

- Controller는 WebAdapter에 위임만 한다.
- 애플리케이션은 JPA·HTTP·SDK를 직접 쓰지 않는다.
- 도메인은 Spring/JPA/웹 DTO에 의존하지 않는다.
- 모듈을 마이크로서비스로 분리하거나 모듈마다 별도 부트 앱을 만들지 않는다. (합의 없는 MSA 전환 금지)

## 6. Setter / AllArgs 남발 금지

| 대상 | 사용 |
|------|------|
| 컨트롤러·서비스·어댑터 | `@RequiredArgsConstructor` + `final` |
| DTO·앱 모델 | 비공개 생성자 + `of`/`from` / 비공개 빌더 |
| 도메인 | 명시적 생성자 또는 `create`/`restore` |
| JPA 엔티티 | `@NoArgsConstructor(PROTECTED)` + 업무용 생성자/팩토리 |

- `@Data`, 클래스 `@Setter` 금지. 필드 setter 기본 금지.
- 상태 변경은 의미 있는 메서드만 (`markMatching`, `assign`, `markSuperseded` 등).
- `@AllArgsConstructor` 거의 금지.

## 7. 프론트엔드 (해당 시)

Atomic Design: Atoms → Molecules → Organisms → Templates → Pages.
한 컴포넌트에 UI·상태·API·업무를 몰아넣지 않는다. 과분리는 피한다.

---

## 8. API 명세 (docs)

- API 명세는 **도메인별**로 `docs`에 작성·유지한다.
  예: `docs/api/matching/`, `docs/api/clinic/`
- API 추가·변경 PR에 명세 갱신을 함께 넣는다.
- 서비스(MSA) 단위가 아니라 **모놀리식 앱의 도메인 API** 기준으로 정리한다.
